# Data model

A search folder looks like this:

```
searches/my-search/
  criteria.yaml          what you want (budget, must-haves, commute, weights)
  listings.json          every unit you have seen (the source of truth)
  listings.template.csv  CSV headers for bulk import
  research/              notes (<listing-id>.md), dossiers/, charts/
  plans/                 floor plans (<listing-id>.json)
  furniture.json         the renter's own furniture: sizes, colours, materials (docs/guides/floor-plans.md#your-furniture)
  sites/                 3D site models (generated)
  layers/                map heat layers (generated)
  cache/                 downloads and geocoder cache (generated)
  history/               claims.jsonl (append-only), snapshots/ (one per build day) and ranks.json (one run per `score`)
  renter_facts.json      numbers you typed for a home's unknowns (written by the dashboard; read by `score`)
  tours/<id>/            findings.json and photos/<photo id>.webp from your visits (written by the dashboard)
  shortlist.md           report (generated)
```

## Listing

```json
{
  "id": "emerald-green-1211",
  "building": "Emerald Green",
  "unit": "1211",
  "address": "320 W 38th St, New York, NY",
  "neighborhood": "Hell's Kitchen",
  "lat": 40.754975, "lon": -73.993195,
  "bbl": "1007610043", "bin": "1087840",
  "beds": 1, "baths": 1, "sqft": 690, "floor": 12, "exposure": ["SSW"],
  "price": {
    "gross": 5021, "free_months": 0, "lease_months": 12,
    "fees_monthly": 29.17, "fees_one_time": 0, "broker_fee": 0,
    "net_effective": null
  },
  "available": "2026-10-16",
  "amenities": {"in_unit_wd": true, "elevator": true, "doorman": "full-time", "gym": true,
                "pool": true, "roof_deck": true, "dishwasher": true, "pets": true},
  "features": {"view": "...", "light": "...", "windows": "...", "interior": "..."},
  "reviews": {"risk": "...", "risk_score": 58, "summary": "...",
              "ratings": [{"label": "Google", "value": "4.0/5 · 35 reviews", "url": "..."}],
              "questions": "..."},
  "status": "shortlist",
  "favorite": "A",
  "notes": "Open questions...",
  "links": {"listing": "https://...", "floorplan": "https://...", "video": "https://..."},
  "checked": "2026-10-04",
  "sources": ["https://..."]
}
```

Generated by the CLI (do not edit by hand): `commute`, `records`, `site`, `score`.

| Field | Type | Notes |
|---|---|---|
| `id` | string | Stable slug. Created from building and unit when missing. |
| `status` | enum | `new`, `researching`, `shortlist`, `touring`, `applied`, `rejected`, `gone`. |
| `favorite` | string | Optional tier label (`S`, `A`, `B`...); favourites float to the top. |
| `price.*` | number | Monthly unless named `one_time`. Unknown = omit or `null`; `fees_monthly: 0` is the only way to say "no fees". See [Money](#money). |
| `size` | object | How the size is known, with a range. See [Money](#money). `sqft` holds reported or exact-plan sizes only. |
| `amenities.*` | bool/null | `doorman` is `full-time`, `part-time`, `virtual` or `none`. Free wording ("24-hour concierge", "laundry in building") is normalised when scoring and flagged `service_wording`. |
| `features_scope` | string/object | Where the `features` wording comes from: `exact-unit` (default) or `same-line`, `building`, `representative`; per key (`{"view": "building"}`) or for all. Only exact-unit wording is scored. |
| `claims` | list | Received source captures: `{field, value, source, observed_at, status}` or `{source, observed_at, price: {...}}`. `status: superseded` drops one. Disagreeing live claims give price scenarios. |
| `exposure` | list | Compass points of the main windows (`N`, `SSW`, ...). |
| `exposure_source`, `exposure_basis`, `exposure_evidence` | text | `exposure_source`: where `exposure` came from (`listing`, `plan`, `agent`, `photo-landmarks`, `model`, `assumed`). `exposure_basis`: a few words on what it rests on ("renter photos + park sightline"). `exposure_evidence`: the longer note, which photo, plan or landmark shows the direction and where. With a basis the site build also keeps the `sightline` comparison of every facade. `assumed` means nothing says which way the windows face (a bearing typed on the command line, or a guess): scoring counts the light result at half strength, pulled toward neutral, and flags it `exposure_assumed`. The site study copies its own source into `site.exposure_source` so the scorer sees it without opening the site file. |
| `window_face`, `window_t` | int, 0..1 | The facade (edge index in the site file's `faces`) and the position along it for the 3D window, when the bearing alone is ambiguous. `window_position_source` says where they came from (`listing`, `plan`, `agent`, `photo-landmarks`, `model`, `assumed`). |
| `floor_inferred` | bool | Set when the floor was guessed from the unit number. |
| `building_facts` | object | `{year_built, floors, source, checked}`: the building's age and height from NYC PLUTO (`source` names the dataset, `64uk-42ks`, looked up by `bbl`; `checked` is the date). Either number may be absent when PLUTO has none (new buildings often have no floor count). Scoring reads it for the building-quality part (year built: 1960 = 0, 2020 = 100; floors: 5 = 0, 40 = 100). If the unit's `floor` is above `floors`, check the `bbl` (it is probably the wrong lot). |
| `photo_review` | object | The unit's photos graded against a written rubric (`method`, `reviewed` date, `evidence` note naming the photos used). Grades are 1-5: `interior`, `kitchen`, `bath`, `natural_light`, `view` (with a `view_note`), `building_luxury` (lobby and amenity photos). Labels: `renovation` (`new-or-recent`, `updated`, `dated`, `unclear`), `appliances` (`premium`, `modern-stainless`, `standard`, `dated`, `unseen`), `floors`, `windows` (`floor-to-ceiling`, `large`, `standard`, `small`, `unseen`). `scope` says what the photos show: `unit`, `mixed`, `staged-or-rendered` (pulled toward neutral) or `building-only` (ignored for the unit); `confidence` is `high`, `medium` or `low`. Feeds the interior part, the light and view part (blended half and half with the sun model) and the building part. A grade you did not see is omitted, not guessed. |
| `photos_meta` | list | One object per saved photo that needs a credit line beyond what `photos` carries: `{url, local, scope, source, credit, title, page}`. `scope` is `exact-unit`, `same-line` or `same-building` (a different unit in the same building); `credit` is the owner's attribution and `page` the page the image came from. Show the credit with the image and never present a `same-building` photo as this unit. |
| `waived_must_have` | list | Must-have keys (`in_unit_wd`, `elevator`...) the renter accepted this unit without. They are still scored, but no longer fail or hold the unit at a gate. Only the renter sets it. |

## Tour findings

What the renter observes in a home is kept **beside** the listing, in `tours/<listing id>/findings.json` (the dashboard writes it when
served with `apartmentscout serve`; the picks backup carries the same record under `findings`). It never edits `listings.json`.

```json
{
  "v": 1, "observed": "2026-10-14", "visited_at": "2026-10-14T15:30", "updated": "2026-10-14T19:40:00Z",
  "rooms": [{"name": "Living room", "w": 13.5, "l": 16}], "ceiling": 8.5,
  "water": 2, "noise": {"rating": 4, "db": 58.4}, "signal": 3, "closets": 2, "laundry": "building", "smells": ["damp"],
  "light": {"rating": 2, "time": "15:30", "facing": "N"}, "view": "Brick wall across a light well",
  "checks": {"wd": {"verdict": "differs", "observed": false}, "doorman": {"verdict": "match"},
             "size": {"verdict": "differs", "observed": 611}, "exposure": {"verdict": "differs", "observed": "N"}},
  "note": "...", "photos": [{"id": "abc123def4", "store": "disk", "w": 1200, "h": 900, "bytes": 81234, "caption": "Bedroom window"}],
  "promoted": {"wd": {"value": false, "observed_at": "2026-10-14", "promoted_at": "2026-10-14T20:00:00Z", "source": "renter, observed on a tour"}}
}
```

Lengths are feet, `water` and `noise.rating` run 1 to 5 (5 is strongest, 5 is loudest), `signal` is bars (0 to 4), `light.facing` is one of
eight compass points. Everything is clamped and cleaned on the way in (`tours.normalize`; the browser's `normalize` is the same rule,
tested against it).

| Check | Listing field it is about | Observed value |
|---|---|---|
| `wd` | `amenities.in_unit_wd` | `true` or `false` |
| `doorman` | `amenities.doorman` | `full-time`, `part-time`, `virtual` or `none` |
| `size` | `sqft` | square feet |
| `exposure` | `exposure` | a compass point |

A check is **contradicted** when the renter marked it *differs* and the value really differs from the listing (size by more than 2
percent, exposure by more than one compass octant); it **adds** a fact when the listing is silent. Neither changes a score by itself.

**Promotion.** `promoted.<check>` is the dated, sourced claim, in the shape of a `claims[]` entry (`tours.claim_of` gives
`{field, value, source, observed_at, status: "live", via: "tour"}`, for example `{"field": "amenities.in_unit_wd", "value": false, ...}`).
It counts only while the renter's check still says the same value. Scoring reads the listing with the promoted facts applied to a copy
(`tours.overlay`): `apartmentscout score`, `export` and the dashboard all do this, so a missing must-have found on a visit fails its gate
and the amenities and size parts move; the exposure and the rest of the light part refresh on the next `apartmentscout score`.

**What an unpromoted contradiction adds to `score`:** a gate `contradicted:<field>` (`in_unit_wd`, `doorman`, `sqft`, `exposure`, appended
after the other gates; it does not affect `eligible`), the tag `differs on tour`, and a line starting `tour <date>:` in the `items` of the
matching reason (`amenities`, `space` or `light_view`), such as `tour 2026-10-14: no in-unit washer/dryer observed, the listing says
in-unit washer/dryer. Not scored until you promote it.` A promoted fact gets a line saying so instead.

**Decision trail.** The picks backup's `history` is a list of revisions: `{e, home, at, kind, from, to, why}` where `kind` is `star`, `tier`,
`status`, `note`, `tour`, `promote` or `unpromote`, `at` is a UTC timestamp and `why` the renter's optional reason (at most 400
characters; the trail keeps the newest 600 revisions). The shared page carries at most 40 per home and the text of a note and the reasons
only when the notes are included.

## Money

Optional price fields beyond `gross`, `net_effective`, `free_months`, `lease_months`, `fees_monthly`,
`fees_one_time` and `broker_fee`:

```json
"price": {
  "gross": 6000,
  "fees": [{"name": "amenity", "amount": 85, "period": "monthly"},
           {"name": "move-in", "amount": 500, "period": "one_time"},
           {"name": "parking", "amount": 450, "period": "monthly", "optional": true}],
  "deposit": 6000, "application_fee": 20,
  "upfront": {"nonrefundable": 0, "refundable": 0, "note": "..."},
  "concession": {"free_months": 2, "lease_months": null,
                 "conditions": [{"type": "start_before", "value": "2026-11-15"},
                                {"type": "new_residents_only"}]}
}
```

| Field | Notes |
|---|---|
| `fees_monthly` | Total required monthly fees: a number, `[lo, hi]` or text like "50-100". Absent or `null` = unknown. |
| `fees[]` | Itemised schedule (`period`: `monthly` or `one_time`; `refundable`; `optional` items never count). Fills in when `fees_monthly` / `fees_one_time` are absent. |
| `deposit`, `application_fee`, `upfront` | Upfront cash. Deposits and `upfront.refundable` are refundable; the rest is spread over the lease. |
| `concession.free_months` | A number, or `[lo, hi]` when a range is advertised (then ranked at gross). |
| `concession.conditions[]` | `start_before` / `lease_start_by` (date), `expires` / `sign_by` (date), `unit_not_named`, `min_lease_months` (number), `new_residents_only`, `immediate_only` or any other note. The same list can sit flat as `concession_conditions` next to `free_months` / `lease_months`. |
| `basis` | Where the rent was read (alias: listing-level `price_basis`). Quoted as is: `unit_page`, `owner_page`, `leasing_office`, `renter_quote`, `broker_card`. **Weak** (ranked on gross, cost range, `unverified:price` gate): `search_snippet`, `building_page`, `received` (an undated copy), `stale` (page known to be old or delisted), `estimate`. Absent = no claim either way. |
| `source`, `checked` | Plain words for the page or person behind the price (no local paths) and the date it was read; `checked` falls back to the listing's `checked`. |
| `range` | `[low, high]`: an advertised range such as RentHop's "$4,318-$4,652". `gross` is the high end; the low end is the best case in `score.cost.price_range`. A range has no term, so it never becomes a net. |
| `note` | One sentence on what the price is and is not (for example "lease assignment through 2/27/27; the 12-month lease is $5,557"). |

`score.cost` for the price above (written by `apartmentscout score`; empty keys are left out):

```json
"cost": {"monthly": 6128.33, "monthly_range": [5128.33, 6128.33], "fees_known": true,
         "unknown": ["lease term"],
         "rent": {"gross": 6000, "basis": "conditional", "free_months": 2,
                  "illustrations": [{"lease_months": 12, "free_months": 2, "net": 5000},
                                    {"lease_months": 14, "free_months": 2, "net": 5142.86}]},
         "paid_month": 6085, "fees_monthly": 85, "fee_items": ["amenity $85/mo", "move-in $500 once"],
         "one_time_spread": 43.33,
         "upfront": {"first_month": 6085, "deposit": 6000, "one_time_fees": 520},
         "move_in_min": 12605,
         "concession": {"free_months": 2, "applies": true,
                        "notes": ["only for leases starting by 2026-11-15", "new residents only"]},
         "assumptions": ["lease term not stated: one-time fees spread over 12 months"],
         "headroom": {"Target": -1128.33, "Stretch": -928.33, "Slightly over": -678.33},
         "concession_needed": {"target": 5000,
                               "12": {"rent_only": 2.0, "rent_only_ask": 2.0, "with_fees": 2.17, "with_fees_ask": 2.5},
                               "18": {"rent_only": 3.0, "rent_only_ask": 3.0, "with_fees": 3.25, "with_fees_ask": 3.5}}}
```

| Key | Meaning |
|---|---|
| `monthly` | First-lease monthly equivalent from the known parts; what `monthly_cost`, tiers and ranking use. |
| `fees_estimate` | Present only when the fees are not documented (no fee sheet, or a condo rental with no one-time package): `{monthly, high, parts[]}`. `monthly` is what ranking adds, the median known monthly fee of buildings with the same doorman level and, for condo rentals, the median known move-in and application package spread over the lease; `high` is the 90th-percentile case; `parts` says in words what was assumed and from how many known sheets. Dropped as soon as the listing has its own fee figures. |
| `monthly_expected` | `monthly` plus `fees_estimate.monthly`, present with `fees_estimate`. It is what the score's `monthly_cost`, the budget tier and the dashboard's price show (marked "est."), so a unit with unknown fees is not ranked as if they were zero. `monthly` stays the documented first-lease equivalent. |
| `monthly_range` | `[best, worst]`: best uses a conditional concession or the cheapest capture; worst is `null` (open) while fees are unknown. |
| `fees_known`, `all_in` | Whether monthly fees are known; `all_in` is set only when they are known exactly. |
| `rent.basis` | `gross` (no concession), `stated` (source's net), `computed` (free months over a stated term) or `conditional` (free months without a term: `illustrations` at 12 and 14 months, no net). |
| `paid_month` | Cash in a month you pay: gross + known monthly fees. |
| `upfront`, `move_in_min`, `move_in_unknown` | First month, deposit, nonrefundable one-time fees and `other_refundable` (refundable items besides the deposit); the minimum cash to move in from documented items, and which items are undocumented. |
| `fee_items` | Readable lines from the itemised `fees[]` schedule. |
| `renewal_base` | Present when it differs from the gross. |
| `concession` | `applies`, `excluded` (why not applied), `notes` (conditions to confirm), `term_from_condition`. |
| `scenarios`, `dispute` | One row per disagreeing price capture; ranking uses the most expensive. |
| `price_basis`, `price_unverified`, `price_checked`, `price_source` | Present when `price.basis` is set; `price_unverified` is true for a weak basis (the `unverified:price` gate and the "price unverified" tag follow). |
| `price_range` | `[best, worst]` monthly cost from the price's own uncertainty, fees as documented: the cheaper reading (the low end of `price.range`, or a quoted net that was not trusted) and the seen rent plus `scoring.unverified_price_band` (default 0.05). Weak prices only. |
| `rent.net_unverified`, `rent.range` | A net quoted by a weak source and not used for ranking; the advertised range. |
| `budget_amount` | Present when `budget.basis` is `gross` or `net`: what the tiers compared. |
| `headroom` | Room under each tier and the hard cap (negative = over). |
| `concession_needed` | For listings above the first tier: free months that reach it, per 12 and 18 month term. |

Size (listing field):

```json
"size": {"sqft": 640, "basis": "line_band_plan", "range": [600, 690], "main_rooms_sqft": null,
         "source": "plan of 12C, same line two floors up", "checked": "2026-10-10"}
```

`basis`: `reported`, `exact_plan`, `line_band_plan`, `main_rooms_sum` or `ratio_proxy` (aliases such
as "advertised", "tier plan", "stated rooms" and "estimate" are normalised). Give `range` when you
know it; otherwise a default band is used (see [methodology](methodology.md#size)). For
`main_rooms_sum`, `main_rooms_sqft` alone is enough. A bare `sqft` is a reported size.

## Photos

Optional fields. See [photos](photos.md) for sources, licences and privacy.

```json
"photos": ["https://portal.example/unit-507-living.jpg", "media/the-unit-507/plan.jpg"],
"photos_local": ["media/the-unit-507/unit-507-living-1a2b3c4d.jpg", "media/the-unit-507/plan.jpg"],
"building_photos": [
  {"url": "https://upload.wikimedia.org/wikipedia/commons/thumb/.../960px-Example.jpg",
   "page": "https://commons.wikimedia.org/wiki/File:Example.jpg",
   "title": "Example Tower from the west", "author": "Jane Doe",
   "license": "CC BY-SA 4.0", "license_url": "https://creativecommons.org/licenses/by-sa/4.0",
   "source": "Wikimedia Commons", "scope": "building", "distance_m": 42, "year": 2023,
   "width": 960, "height": 1280, "local": "media/the-unit-507/960px-Example-5e6f7a8b.jpg"}
]
```

| Field | Type | Notes |
|---|---|---|
| `photos` | list of strings | The listing's own photos: portal or building-site URLs, or `media/<id>/<file>` paths. Copyrighted by their owners; private searches only. |
| `photos_local` | list of strings | Saved copies of `photos` under `<search>/media/`, written by `apartmentscout photos --cache`. Show these first; the URLs can die. |
| `building_photos` | list of objects | Licensed photos of the building or its street, best first. Written by `apartmentscout photos` (Commons entries are replaced on each run; entries from other sources are kept). |
| `building_photos[].url` | string | Image to show, about 960 px wide. |
| `building_photos[].page` | string | Where the licence and full credit live; link the credit line here. |
| `building_photos[].author`, `license`, `license_url` | string | Plain-text credit. Show `author` and `license` with every image. |
| `building_photos[].source` | string | `Wikimedia Commons`, or where an agent found it (`Building website`, ...). |
| `building_photos[].scope` | enum | How close the photo is to the unit: `exact-unit`, `same-line` (same tier on another floor), `building`, `street` (the block, not this building), `aerial`. |
| `building_photos[].title` | string | The file's title, for alt text. |
| `building_photos[].distance_m` | number | Camera position to the listing, metres (Commons only). |
| `building_photos[].year` | number | Year taken when Commons records it; show it, buildings change. |
| `building_photos[].width`, `height` | number | Size of `url` in pixels. |
| `building_photos[].local` | string | Saved copy under `media/`, private searches only. |
| `floorplan_images` | list of strings | Floor plan images: links and saved copies (`media/...`). The dashboard shows the saved copy and keeps its link as a fallback. |
| `photos_meta` | list of objects | Parallel to `photos` and `photos_local` (same index). Each entry may carry `scope`, `title`, `credit` (one line), `source` and `page`. A photo with no entry is the exact unit. |
| `photos_meta[].scope` | enum | `exact-unit` (the unit itself), `same-line` (same stack, another floor) or `same-building` (another unit or a common area). Decides the lightbox group. |
| `photo_flags` | object | Per listing, keyed by a saved photo path (the string in `photos_local`, `building_photos[].local` or `floorplan_images`): `{"watermark": true, "why": ["phone number"]}`. Marks a photo that carries a broker's phone number, logo, web address, e-mail or a person's face. The dashboard keeps it but orders it last in its group and badges it. Written by `scripts/apply_photo_flags.py` (idempotent: only this field changes) from a review pass whose output maps each photo path to `{"why": [...], "uses": [[listing id, kind]]}`. |

### Photo groups and order

Every dashboard surface (cards, drawer, lightbox, Research gallery, Shortlist thumbnail) sorts a listing's images the same way
(`dashboard/js/features/photos.js`). The group comes from the scope: a listing's own photo is **unit** unless its
`photos_meta` says otherwise, `same-line` is **line**, `same-building` and building photos are **building**, `street` photos are
**street**, and floor plans are **plan**. The order is unit, same line, building, floor plans, street; inside a group a photo
flagged in `photo_flags` goes last and otherwise the data order holds. A card's photo is the first unit, line or building image,
never a plan. The card's count reads "8 unit · 22 building".

### The home the 3D views open: `search.default_listing`

`search.default_listing` in `criteria.yaml` is the id of one listing. `criteria --check` rejects a value that is not an id and warns
when `listings.json` has no such listing (or marks it `gone` or `rejected`); `apartmentscout build` copies a listing that exists into
`manifest.json` as `default_listing`, so no listing id lives in the dashboard's code. Unit 3D, the Floor plan studio (so the 3D tab) and
Records open that home when the address names none (`#unit`, `#plan`), in this order: the home in the address; the home the view showed
earlier in the session; the home the renter opened last in this browser (local storage `as:home-id`, written when the address names a
home, never for the default); `default_listing`; the first home in the list. The bundled example sets it to Paramount Tower 25E.

### Where a saved photo comes from: `media/`, `media-lite/`, `media_base_url`

A listing's saved photos are paths such as `media/<listing-id>/p-1a2b3c4d.webp` or `media/shared/<hash>.webp`. Which copy of a
path exists depends on where the page runs, so the dashboard asks for each photo in the same order everywhere (a plain static
server, `apartmentscout serve`, the published site, the share and tour pages) and moves on at the first miss:

1. `media/<path>`: the full set next to the page (`<search>/media/`; a private search has nothing else).
2. `media-lite/<path>`: a **starter set** with the same relative paths, small enough to keep in the repository.
3. `<media_base_url><path under media/>`: the published full set.
4. The photo's original link (`photos[i]`), then the card's aerial view or glyph.

`search.media_base_url` in `criteria.yaml` names the published folder (an `https://` folder URL, validated by `criteria --check`):

```yaml
search:
  media_base_url: https://0marm0.github.io/ApartmentScout/demo/media/
```

`apartmentscout build` copies it into `manifest.json` as `media_base_url`, so no URL lives in the page's code. Without the line a
search has no published copy and step 3 is skipped. In `apartmentscout serve`, `/media/<path>` answers from `media/`, then
`media-lite/`, and sends anything else to the published copy with a `302`. A page served by a plain static server tries each step
with an `onerror` fallback: one chain per image, remembered for the session, and a folder that has failed three times without ever
answering is skipped from then on (`dashboard/js/features/media-chain.js`). The single-file build (`build --standalone`) has no media
folders beside it, so it starts at step 3 (`manifest.media_local: false` in the embedded copy); without a `media_base_url` it
falls back to the photos' original links, as before.

The bundled example uses all the tiers: the full 5,595-photo set (about 400 MB) is a GitHub release that the Pages workflow
publishes at `/demo/media/`; `examples/nyc-2026/media-lite/` (34 MB, tracked) holds the starter set; and
`examples/nyc-2026/media/` is ignored and only exists if you run `scripts/fetch_media.sh`. The starter set is built by
`scripts/make_media_lite.py`: a full gallery (up to 30 photos, clean ones first) for the top 12 active listings by `score.rank`
and for Paramount Tower 25E, the hero plus one building photo, re-encoded smaller, for every other listing that has photos,
and every floor plan that is a local file. Its `MANIFEST.json` records the settings and the counts.

### Blur-up previews: `lqip.json`

`apartmentscout build` writes `data/lqip.json` next to `listings.json` when Pillow is installed (`pip install 'apartmentscout[images]'`;
without it the build says so and the dashboard simply fades photos in). It holds a 24 px wide WebP per leading photo, the first of
each of the unit, same-line and building groups of every listing, base64 encoded, a few hundred bytes each:

```json
{"v": 1, "w": 24, "fmt": "webp", "items": {"media/the-unit-507/p-1a2b3c4d.webp": [1200, 800, "UklGR..."]}}
```

Keys are the saved photo path; each value is `[source width, source height, base64]`. `manifest.json` says `"lqip": true` when the file
was written. The dashboard fetches it beside the main data (never inside `listings.json`, which stays the same size), paints each preview
blurred behind its photo and cross-fades when the photo arrives, and uses the pixel size as the layout ratio in the Research gallery.
Previews are cached by file size and modification time in `<search>/cache/lqip.json`, so a rebuild only reads photos that changed.
A photo that is not on this machine (the full set was never downloaded, or was deleted to free space) keeps the preview already in
`lqip.json`; only a photo with no earlier preview is read from `media-lite/`. The example's sidecar is about 150 KB for 495 photos.
The standalone file embeds it when it is under 400 KB. With a `media_base_url` the previews stay keyed by the saved path; without one,
and without a `media/` folder beside the file, they are re-keyed by each photo's original link.

## Commute

`commute` is written by `apartmentscout commute`, one entry per destination name:

```json
"commute": {"Office": {
  "minutes": 26.3, "mode": "transit", "route": "walk 1 min to E 14 St/Avenue C → bus M14D-SBS to E 14 St/Irving Pl → 4 to Grand Central-42 St → walk 5 min to destination",
  "modes": {
    "walk":    {"minutes": 41.6, "m": 3330, "route": "walk 42 min"},
    "subway":  {"minutes": 28.5, "range": [27.0, 30.5], "route": "walk 10 min to 1 Av → L to 14 St-Union Sq → 4 to Grand Central-42 St → walk 5 min to destination",
                "via": "subway", "transfers": 1, "ride_min": 6.5, "walk_min": 18.1, "wait_min": 2.0,
                "legs_arrive_by": "08:54", "legs": [
                  {"mode": "walk", "min": 10.5, "m": 683, "to": "1 Av"},
                  {"mode": "subway", "route": "L", "from": "1 Av", "to": "14 St-Union Sq", "board": "08:30", "alight": "08:32", "min": 2.5},
                  {"mode": "transfer", "min": 3.0, "m": 84, "at": "14 St-Union Sq"},
                  {"mode": "subway", "route": "4", "from": "14 St-Union Sq", "to": "Grand Central-42 St", "board": "08:38", "alight": "08:42", "min": 4.0, "wait": 2.0},
                  {"mode": "walk", "min": 4.6, "m": 212, "from": "Grand Central-42 St", "to": "destination"}]},
    "bus":     {"minutes": 30.5, "range": [28.1, 31.1], "route": "...", "via": "bus", "legs": [...]},
    "transit": {"minutes": 26.3, "range": [25.1, 28.1], "route": "...", "via": "mixed", "legs": [...]}}}}
```

| Field | Notes |
|---|---|
| `minutes`, `route` | Best of any transit and walking (= `modes.transit`); what scoring and sorting use. |
| `mode` | `walk` when walking is fastest, else `transit` (unchanged from the single-mode router). |
| `modes.walk.m` | Walking metres (street-grid metric inside a city grid, else straight line x detour). |
| `modes.<m>.minutes` / `range` | Mean and min-max over the sampled arrival times. One key per mode in the feeds (`subway`, `bus`, `rail`, `ferry`) plus `walk` and `transit`. |
| `modes.<m>.via` | `walk`, `subway`, `bus`, `rail`, `ferry` or `mixed`: what the typical trip rides. |
| `modes.<m>.legs` | The median trip: `walk` (`min`, `m` metres, `to`, `from`), rides (`mode`, `route`, `from`, `to`, `board`/`alight` clock times, `min`, `wait` before boarding after a change), `transfer` (`min`, `m`, `at`, `to` when it changes stop). Walking minutes include street-to-platform time. |
| `modes.<m>.legs_arrive_by` | The arrival time that trip was planned for (arrive_by minus one of the offsets). |
| `transfers`, `ride_min`, `walk_min`, `wait_min` | Totals over the legs. |

Route text reads `walk N min to <stop>`, `<route> to <stop>` for subway and rail, `bus <route> to
<stop>` and `ferry <route> to <stop>`, joined by ` → `.

## Score

`score` is written by `apartmentscout score` (version 2.0; the first nine keys are unchanged from 1.x):

```json
"score": {"overall": 72.2,
          "parts": {"cost": 85, "space": 47, "commute": 100, "amenities": 82, "light_view": 61,
                    "building": 74, "quiet": 51, "move_date": 100, "renewal_risk": 25, "transit_access": null},
          "confidence": 90, "range": [65.1, 77.3], "monthly_cost": 5050.2,
          "budget_tier": "Stretch", "gates": ["unverified:in_unit_wd", "unverified:fees"], "eligible": true,
          "rank": 8,
          "version": "2.0", "preset": "balanced",
          "ranks": {"fit": 11, "action": 8, "budget": null, "building": 6},
          "part_ranges": {"space": [38.0, 56.1]},
          "reasons": [{"dim": "commute", "pts": 7.5, "text": "+8 commute: 9 min to Office by subway"},
                      {"dim": "space", "pts": -0.4, "text": "0 space: ~610-710 ft² (same-line plan)",
                       "items": ["scored at the 660 ft² middle; the range is kept in the score range"]}],
          "flags": ["fees_unknown", "floor_inferred", "size_estimated"],
          "tags": ["thin data"],
          "ppsf": {"value": 7.65, "range": [7.12, 8.28], "basis": "line_band_plan"},
          "cost": {"...": "see Money"}}
```

| Key | Meaning |
|---|---|
| `parts` | One 0-100 score per dimension, `null` when unknown (counted as 50). |
| `rank` | Same as `ranks.action`, kept for older readers. |
| `ranks` | `fit` (all scored listings, status-blind), `action` (eligible only), `budget` (eligible and inside the first tier), `building` (buildings ordered by their best eligible unit). `null` when not in that pool. |
| `part_ranges` | Dimensions whose input is a range (size estimate, fee range, conditional concession): the part at either end. |
| `reasons` | One per dimension in dimension order: `pts` = (part - 50) x weight / total weight; `text` = signed rounded points, the dimension label, then a plain summary; `items` = itemised evidence when there is more than the summary. |
| `flags` | Inferred or partial inputs: `fees_unknown`, `fees_estimated`, `exposure_assumed`, `net_conditional`, `lease_term_assumed`, `price_dispute`, `cost_unknown`, `size_estimated`, `size_proxy`, `studio_from_text`, `floor_inferred`, `visual_not_exact`, `service_wording`. |
| `tags` | `thin data` (confidence below 60 %) and `source conflict` (disagreeing captures, or a listing `conflicts` list). |
| `ppsf` | $/ft² from `monthly_cost`; `null` for unknown or ratio-proxy sizes. |
| `cost` | The money model ([Money](#money)). |
| `gates` | Besides `over_budget`, `fails:*`, `unverified:*` and `unknown_cost`: `unverified:fees`, `unverified:lease_term`, `concession:not_applied`, `price_dispute`, `move_date:after_window` (or `fails:move_date` with `move_in.hard`), `stale:checked_N_days_ago`. Only `over_budget` and `fails:*` affect eligibility. |

See [methodology](methodology.md) for how each part is computed.

## Layers

`layers/*.json` are regular lat/lon grids:

```json
{"kind": "commute", "name": "Office", "bbox": [lon0, lat0, lon1, lat1], "rows": 139, "cols": 76,
 "cell_m": 150, "values": [/* row-major from the south-west; -1 = no data */]}
```

`commute-<destination>.json` is the best of any transit (`"mode": "transit"`). With `mode_grids: true`
(the default) the router also writes `commute-<destination>-subway.json`, `-bus.json` and so on, with
`"kind": "commute-mode"`, `"mode": "subway"` and the same grid, so a viewer can toggle modes (about
32 KB each for the Manhattan example). Every commute grid lists the available `modes`.

Other keys of a commute layer: `destination` (`{name, address, lat, lon}`), `arrive_by`, `service_date`, `feeds`
(the timetable names), `arrival_offsets_min` (the minutes before `arrive_by` the router averaged over), `water_masked`,
`method` (one sentence on how the numbers were made) and `generated`. The values are `values_u8` (base64 bytes of
half-minutes, row-major from the south-west, `scale` 0.5, `nodata` 255) in new layers or the plain `values` list in
older ones.

**Network walking.** `walk_model` is `"network"` when walking followed the OpenStreetMap pedestrian network (the
default for NYC) and `"grid"` for the street-grid or straight-line metric; it falls back to `grid` when the network
cannot be fetched. A network layer also carries `walk_network`:

| Key | Meaning |
|---|---|
| `source`, `osm_base` | `OpenStreetMap (Overpass)` and the timestamp of the OSM data the ways came from. |
| `km`, `junctions` | Walkable way length and junction count of the graph the router used. |
| `snap_m` | `walk_snap_m` (default 60 m): a cell farther than this from any walkable way is blank, and a listing takes the fastest of every way within this distance. |
| `entrances` | Station entrances used: `{entrances, stops_with_entrances, stations_with_entrances}`; absent when the city has no entrance source (`station_entrances`). |
| `sources[]` | One receipt per dataset read for the walk (the entrance list, Overpass): `dataset`, `name`, `calls`, `rows`, `limit_hit`, `retrieved`, and `rows_updated` for OSM. |

Each listing's `commute.<dest>.modes.walk.m` is the metres along that network (or the grid metric).

**Combined commute surfaces.** With two or more destinations, `apartmentscout build` adds
`layers/commute-combined-best.json` (and `-subway`, `-bus`) to the dashboard data, from the per-destination grids:
`{"kind": "commute-combo", "mode": "best", "destinations": [{name, weight, max_minutes, lat, lon}], "limit_worst", "limit_weighted",
"bbox", "rows", "cols", "cell_m", "scale": 0.5, "nodata": 255, "worst_z", "weighted_z", ...}`. `worst_z` is the longest trip
to any destination at each cell and `weighted_z` the weight-averaged minutes, each as the usual half-minute bytes, deflated
(zlib) and base64-encoded (inflate with `DecompressionStream("deflate")`). They are listed in `manifest.extra`, not
`manifest.layers`: the dashboard loads them when someone picks them in the map legend.

## Places

`places.json` (`apartmentscout places`; copied to the dashboard data by `build`) is the geometry behind "east of 3rd Ave",
"near Bryant Park" and "in Murray Hill": `streets` (`name`, `keys`: every spelling the search box accepts, `axis`: the
street's direction in degrees, `lines`), `areas` (parks and neighbourhoods: `id`, `name`, `kind`, `keys`, `polys`: a list
of polygons, each an outer ring then holes), `groups` (a name that spans several areas: `members`), `grid`
(`north_bearing`: the street grid's north), `bbox`, `sources` (one receipt per dataset: OpenStreetMap, the neighbourhood
dataset) and `attribution`. Lines and rings are integer 1e-5 degree steps, delta-encoded (`enc: "e5-delta"`):
`[lon0, lat0, dlon1, dlat1, ...]`. About 100 KB for Manhattan; see the methodology's *Place filters*.

Context only: never an obstruction in the sun hours, and the legend says so. `--no-green` skips it; `apartmentscout site <id> --green-only` adds or refreshes it (with the city layers) on an existing site file without rebuilding anything else, `--context-only` also refreshes `water`, and `--keep-osm` keeps the OpenStreetMap parks and trees already in the file (no Overpass call; a refresh that finds Overpass down keeps them on its own). |
| `green.census` | New York only. The street trees of the NYC Street Tree Census 2015 (NYC Parks, Open Data `uvpi-gqnh`; OpenStreetMap maps only a few percent of them): `source`, `dataset`, `date` (the survey year), `fetched`, `q_m` (0.5: coordinates are integer multiples of this many metres), `groups` (crown-colour classes by genus: `other`, `plane`, `oak`, `maple`, `locust`, `linden`, `ornamental`, `elm`, `ginkgo`, `conifer`), `n` and flat `pts` `[x, y, dbh_in, group, ...]` (east and north in the footprints' frame, trunk diameter at breast height in whole inches, index into `groups`), live trees within the site radius, nearest first, at most 6,000, about 14 bytes a tree. `removed` counts the census trees dropped because the current NYC Parks inventory lists them as removed (a stump, retired or dead point within 3 m and no live one). Canopy size is not stored: the views size it from the trunk (crown diameter 1.2 m + 0.19 m per cm of trunk, capped at 16 m, height 1.3 m + 0.62 x DBH(cm)^0.82, capped at 24 m, fitted to typical open-grown urban trees; `geo/trees.py` and `dashboard/js/unit/trees.js` hold the same rule, checked against `tests/fixtures/tree_allometry.json`) after adding 1 in of growth since the survey (the median growth of census trees matched to the live inventory). These are the *street trees* of the layer controls. |
| `green.forestry` | New York only. Straight sight lines over the site's walls, flat ground, trees as 10 m crowns: no terrain, no facade colour. |

| `study.blockers` | The buildings that shade the window: `b` (index into `b`/`bmeta`; the target itself when the sun is around the corner of its own walls), minutes shaded on the 15th of each month (`min`, only while the sun is up and in front of a pane) and the nearest distance along the sun ray (`dist`, m). Top 6 by minutes over the year. |
| `roofs` | Eye height against neighbouring roofs within 150 m of the window. `facing`: the window's sector (bearing +/- 45 degrees) with up to 8 nearest buildings as `[b, dist, top, clears_floor]` (`b` < 0 = `future[-b - 1]`) and `clears_floor`, the lowest floor whose eye height (slab + 1.6 m) is above all of them (null when even `top_floor` is not). `sectors`: eight 45 degree sectors with the 6 nearest `[b, dist, top]`, `max_top` and its `clears_floor`. Bearings point at the nearest part of each footprint. |
| `neighbours` | Every building within 300 m of the window (or the origin), nearest first: `[b, dist, bearing, h, top]` (distance to the footprint's nearest point, bearing to that point, own height and roof relative to the target's ground). | `checks` | Self-checks on the built model, each `{"id", "status": "pass" \| "warn" \| "fail", "msg"}`: `origin` (address point within 15 m of the target), `ground` (target ground is 0), `storey` (clamped storey height), `anchor` (window anchor 0.2 m inside the target), `outside` (open air 0.5-1.5 m outside the window), `outside-future`, `streets` (named streets on opposite sides within 150 m), `future-overlap`, `heights` (more than 25 % guessed heights in front of the window warns), `limits` (a download hit its row limit), `components` (how many buildings were split; warns on problems in the components file) and `window-component` (the unit's own building has components: warns when none reaches the facade behind the window at its height). Printed by `apartmentscout site`. |
| `receipts` | One entry per dataset read: `calls`, `rows`, `limit_hit` (a query returned exactly its `$limit`, so rows were probably cut off), `retrieved`, `rows_updated` (the dataset's own last update, from Socrata metadata; for Overpass the OSM base timestamp) and per query the first 16 hex of the payload's sha256 and the URL when short. Full receipts sit next to the cache as `<cache>/site/*.receipt.json`. |
| `streets` | Street centrelines within the site radius (`width_m` = roadbed width where known). |
| `future` | New buildings filed with or permitted by NYC DOB that are not standing yet. `status`: `proposed`, `permit` (plans approved), `under-construction` (work permit issued), `complete` (not yet in the footprints). `ring_src`: `tax-lot` (the whole lot, an upper bound) or `point` (location only). |
| `provenance` | Where `exposure`, `window_position` (`listing`, `plan`, `agent`, `photo-landmarks`, `model`, `assumed`) and `floor` (`listing`, `inferred`, `assumed`) came from. Filled from the listing's `exposure_source`, `window_position_source` and `floor_inferred`. `basis` and `evidence`: the listing's `exposure_basis` (a short label such as `renter photos + park sightline`) and `exposure_evidence` (the note on which facades were tested and why one won), shown in the Unit 3D evidence panel. `target`: how the building was matched (`bin` = the listing's BIN, `bbl` = its tax lot, `name` = a footprint named like the listing's building within 250 m (OpenStreetMap `name` or the footprint's own), `address` = a footprint with the listing's house number and street within 250 m (`addr:housenumber` + `addr:street`), `point` = the footprint containing the geocoded point, `nearest` = the nearest tall-enough footprint within 45 m); `target_offset_m`: how far the address point lies outside that footprint (over 10 m adds a note). |

The listing gets a summary in `site`: file, floor, bearing, `sun_hours`, `sun_hours_range` (`lo`, `hi`),
`skyline_ahead_deg`, `open_sky_share`, `sky_view`, `daylight_factor_est`, `sun_year` and, where a sunshine
table exists, `sun_hours_expected`.

Manual components live next to the site file as `sites/<id>.components.yaml` and are read on every
`apartmentscout site <id>` (`--no-components` skips only the OpenStreetMap parts):

```yaml
lonlat: false                # true: rings and "at" are [lon, lat]
buildings:
  - select: target           # or {bin: "1012345"}, {bbl: "1008350001"}, {b: 12}, {at: [x, y]}
    components:
      - {kind: podium, ring: footprint, base_m: 0, top_m: 24, source: "DOB zoning diagram, job 123", confidence: high}
      - {kind: tower, ring: [[-10, -60], [10, -60], [10, -40], [-10, -40]], base_m: 24, top_m: 140,
         source: "DOB zoning diagram, job 123"}
```

A components file may also be JSON (`sites/<id>.components.json`, the same structure; used when no YAML file exists). `--eye-height` takes the measured height of the window's eye level above the street
(slab + 1.6 m) instead of `--slab-height`; both end up in `calibration.measured`.

| Key (localStorage) | Meaning |
|---|---|

in every panel), `base`, `scenarios` (each with its `changes`, `state` and `metrics`), `deltas` (every metric per scenario and

window is not in open air.

The model project (`apartmentscout-model-project`, schema 1) is one JSON file: `site` (`id`, `base`, `generated`, `source`, `sha256`
and `data`, the whole site model with its receipts and checks), `receipts`, `anchor`, `pin`, `calibration`
(`apartmentscout-vertical-calibration`), `assumed_parts`, `plan` (`id`, `source`, `label`, `saved` and `project`, a plan
project from the floor plan studio with furniture and lighting), `scenarios`, `comparison`, `edits` (what-if neighbour heights),
`view`, an optional `glb` (`name`, `encoding: "base64"`, `bytes`, `sha256`, `data`) and `app` version metadata. Import is
strict (size, finite numbers, known shapes, no prototype keys) and refuses a bad file with a reason; damaged optional sections
are dropped with a warning.

`apartmentscout site <id> --samples` writes `research/<id>-sun-samples.csv`: every 6 minutes of the move-in
day (listing `available`, else `search.move_in.earliest`) and of Mar 20, Jun 21 and Dec 21, with sun azimuth
and altitude, the state (`night`, `behind`, `lit`, `shaded`) and, when shaded, the blocking building's name or
address, BIN, roof and distance.

### Photo match: `view-calibrations/<id>.json`

Unit 3D's Window camera has a guided **Match a photo** (three steps: pick a listing photo, mark two or more landmarks in it and name each from the
site's `lm` list or by clicking it in the 3D view, check the fit and save). A small solver (`dashboard/js/unit/view-solver.js`) works out which way
the photo looks (`bearing_deg`), its tilt, its lens (`vfov_deg`, vertical) and the height the camera stood at (`eye_height_m`), with the residual
(`rms_deg`, the angular distance between where each landmark was clicked and where the model puts it). Two landmarks fit bearing, tilt and height
with the lens assumed (55 degrees unless set); three or more also fit the lens. Heights and lens are only reported as measured when the clicks can
fix them (`eye_determined`, `lens_determined`; `sigma` holds the one-sigma uncertainties): landmarks that are all far away cannot separate tilt from
camera height, and then the model's height stays. A neighbouring roof clicked in the 3D view usually fixes it.

The record (`kind: "apartmentscout-view-calibration"`, `schema: 1`) holds `site`, `saved`, `photo` (`n` its place in the gallery, `floor` where it was
taken, `scope`, `aspect`), `eye` (the window point and the eye height the fit started from), `landmarks` (`name`, `kind` named or picked, `x`, `y`, `z` in
site metres, `u`, `v` the click as fractions of the picture), `result` and `applied` (`az_deg`, `floor`, `facade_offset_deg`). `apartmentscout serve`
saves it to `<search>/view-calibrations/<id>.json` (a bundled example is read-only, so the page keeps it in the browser and offers **Export**);
`apartmentscout viewcal import FILE` takes an export into a search folder and `viewcal list` shows them; `build` copies the folder to the page and
lists the ids in the manifest's `view_calibrations`. `apartmentscout site <id>` then uses the match: the photo's bearing as the window's facing
(when within 12 degrees of a wall; `--bearing` still wins, `--no-view-calibration` ignores it), and the camera height as a measured `--eye-height`
(scaled to the unit's floor when the photo was taken on another floor: every storey is stretched to fit). The site file keeps what it used in
`calibration.view`, and the accuracy chip reads "measured from photo N" for the facade bearing and, when the photo fixed it, the floor height.

### Unit aliases

A listing can declare other listing ids for the same unit in `aliases`, or other spellings of its unit in
`unit_aliases` (for example `["13CA"]` on 13C once the leasing office confirms they are one unit).
`listings.merge_aliases()` folds them into the first listing (filling its missing fields, recording
`alias_ids`) so the unit is shown and scored once. Aliases are never inferred from the letters of a unit
label: 13B and 13BA stay separate unless declared.

## Renter facts

`renter_facts.json` in the search folder holds the numbers the renter typed for a home's unknowns in the dashboard's *Unknowns that move
this score* section. It never changes `listings.json`: `apartmentscout score` applies each one to a copy of the listing, marks it in
`score.renter` (`{"size": {"value": 640, "at": "2026-10-15", "source": "renter"}}`) and flags it `renter:size` in `score.flags`.

```json
{"v": 1, "facts": {"the-knox-6b": {"size": {"value": 640, "at": "2026-10-15", "source": "renter"}}}}
```

| Kind | Value | Read as |
|---|---|---|
| `size` | ft² (50 to 20,000) | the unit's reported size: no estimate, no range |
| `fees` | $ a month (0 to 20,000) | the required monthly fees, known (0 means none) |
| `price` | $ a month (100 to 100,000) | the rent you will pay each month after free months, from a written quote (`price.basis: renter_quote`): ends a price dispute and an unverified-price gate |
| `wd` | true / false | the in-unit washer/dryer: confirmed, or a failed must-have |
| `floor` | 1 to 120 | the floor, no longer inferred |

The dashboard computes the same re-score in the browser (`dashboard/js/features/facts-model.js`), so a typed number re-ranks the home at
once; `tests/test_renterfacts_parity.py` keeps the two in step.

## History

See [research quality](research-quality.md#history) for the rules. Files in the search folder:

- `history/claims.jsonl`, append-only, one claim per line:
  `{"id", "field", "value", "source", "source_kind", "claimed_at", "received_at", "method", "scope", "note", "logged_at"}`.
  `field`: `status`, `gross`, `net`, `fees_monthly`, `fees_one_time`, `free_months`, `lease_months`,
  `available`, `sqft`, `concession`, `note`. `source_kind`: `unit_page`, `building_site`, `portal_search`,
  `broker`, `leasing_office`, `partner`, `renter`, `agent`, `cached`, `other`. `claimed_at` = the day the
  source says the fact was true (may be null: undated); `received_at` = the day it reached the search.
- `history/snapshots/YYYY-MM-DD.json`: `{"schema_version": 1, "date", "fields": [...], "listings": {id: [values]}}`
  with `fields` = `status, gross, net, fees_monthly, free_months, lease_months, available, checked, key`
  (`key` = normalised building address + unit, used to spot relists under a new id).

- `history/ranks.json`: where every home stood on each `apartmentscout score` run, so the dashboard can say why a home moved.
  Columnar and small (about 40 KB a run for 738 homes; six runs at most; a rescore on the same day with the same scoring version
  replaces that day's run, and a run that repeats the last is not stored). `{"v": 1, "dims": [...], "vocab": [...], "versions": {"2.1":
  "what it changed"}, "ids": [...], "runs": [{"at": "2026-10-13T23:45", "version": "2.0", "k": 10, "w": [weights in dims order],
  "n": 335, "a": [action rank, 0 = none], "f": [fit rank], "s": [overall x 10, -1 = none], "c": [monthly cost, -1 = unknown],
  "p": "two hex digits per dimension per home, ff = unknown", "g": ["dot-joined indexes into vocab: the flags and gates", ...]}]}`.
  `build` copies it to the dashboard as `ranks.json` once it holds two runs. The bundled example's history was seeded from the git
  history of its scored `listings.json`.

Optional listing fields read by history and lint: `price_history` (`[{"date", "gross"}]`, earlier prices from
a portal's history), `listed_at` (the date the source says the unit was listed; never inferred from a check
date), `address_aliases` (other street addresses of the same building).

A search can start with history taken from an earlier research record: every price point is a `gross` or `net`
claim whose `claimed_at` is the day that price was shown and whose `source` names the file it came from (a path
relative to the research folder, never an absolute one), and a status claim is only written for a listing that
stayed gone (a relisted unit keeps its price points instead). The bundled `examples/nyc-2026/history/claims.jsonl`
is built this way. A claim about a listing whose `status` still reads active is dated by the check that found it,
with the event's own date in `note`, so the availability ladder does not report a dispute with itself.

Monitor files, written by `apartmentscout monitor` (see [monitoring](monitoring.md)) under `history/monitor/`:
`observations.jsonl` (append-only; one line per page fetched: `{"id", "url", "host", "fetched_at", "status",
"observation": {"gross", "net", "free_months", "lease_months", "status", "available", "method", "note"}, "sha"}`),
`cache/<hash>.json` (the last reading per URL, with `fetched_at` and `status` `ok` or `blocked`),
`digests/YYYY-MM-DD.md|json` and `digest.json` (the latest). Changes it finds also go to `claims.jsonl` with
`method: "monitor"`. criteria.yaml:

```yaml
monitor:
  allow_hosts: [example-tower.com]   # hosts that may be fetched; portals are never fetched unless named here
  max_age_hours: 12                  # reuse a reading younger than this
```

```json
                                 {"date": "2026-10-09", "gross": 4950, "net": null, "source": "snapshot"}]},
 "availability": {"tower-12b": {"state": "conditional", "reason": "unconfirmed: in unit wd", "as_of": "2026-10-09"}},
 "summary": {"snapshots": 3, "claims": 2, "events": 14, "gone": 4, "numeric_days": 2,
             "median_days_to_gone": 6.5, "availability": {"conditional": 20, "gone": 17}}}
```

| Key | Meaning |
|---|---|
| `note` | Set (and the lists empty) when there are no snapshots or claims yet. |
| `snapshots[]` | One row per snapshot, oldest first: listings in it and how many were not gone or rejected. |
| `events[]` | Newest first. `type`: `new`, `relist` (back from gone, or the same building and unit under a new id: `field: "id"`), `price` (`field` `gross`, `net` or `fees_monthly`), `concession` (`free_months`, `lease_months`), `status` (`field` `status`, or `available` when the date moved: a change, never a new listing), `gone` (`note` says when the row was removed instead), `claim` (a logged claim; `date` is its `claimed_at`, or `received_at` with a note when undated). |
| `gone_fast[]` | Every listing seen going gone. `listed` comes from `listed_at`, or the first snapshot that saw it active when that is not the very first snapshot; otherwise null, and so is `days`. Sorted fastest first, unknown last. |
| `price_history` | Listings with two or more distinct price points (snapshots and dated price claims). |
| `availability` | The availability ladder state for every listing (extension). |

## Coverage

`coverage.json` (dashboard export; `apartmentscout coverage --json` prints the same document):

```json
{"schema_version": 1, "generated": "2026-10-13", "stale_days": 7,
 "claim": "Coverage of the listings this search has captured. It is not a market census: ...",
 "standard": [{"key": "rent", "label": "Gross rent", "why": "..."}],
 "listings": {"tower-12b": {
    "have": ["rent", "must_haves"], "missing": ["fees", "size"], "stale": ["status"],
    "score_impact": 18.4, "rank": 6, "rank_range": [2, null],
    "gaps": [{"key": "size", "impact": 14.0}, {"key": "fees", "impact": 2.1, "gate": true}],
    "priority": 3, "priority_reason": "finalist with open facts", "active": true, "finalist": true,
    "questions": ["Please list every required monthly charge ..."],
    "lint": [{"code": "stale_or_cached_page", "severity": "med", "message": "...", "field": "checked"}]}},
 "sources": [{"name": "StreetEasy", "listings": 40, "active": 31, "checked": "2026-10-12", "sweeps": 2,
              "state": "complete"}],
 "summary": {"listings": 58, "active": 41, "complete": 3, "finalists": 8, "finalists_complete": 1,
             "missing_size": 20, "missing_fees": 33, "missing_media": 12, "stale": 9,
             "statuses": {"researching": 30}, "flags": {"junior_or_flex_1br": 2}, "median_score_impact": 12.5},
 "gaps": [{"key": "fees", "label": "Required monthly fees", "missing": 33, "stale": 0, "of": 41,
           "impact": "33 of 41 have no fee schedule: budget tiers are a discovery filter until fee sheets arrive."}]}
```

| Key | Meaning |
|---|---|
| `standard[]` | The facts a finalist needs, in question order. `bedroom` appears only when `unit.min_beds` >= 1, `commute` only with destinations. |
| `listings.<id>.have / missing / stale` | Disjoint lists of standard keys. `stale`: known, but `checked` is older than `stale_days` (rent, concession, fees, start date, status only). |
| `score_impact` | Overall score swing in points between the pessimistic and optimistic answers to every missing fact. |
| `rank` / `rank_range` | Current rank, and `[best, worst]` rank among the other eligible listings after those answers; `null` worst = the pessimistic answer fails a gate (often unknown fees over the cap). Both null for gone and rejected listings. |
| `gaps[]` | Missing facts that move the score, largest first: `impact` in points; `gate: true` when the pessimistic answer fails a gate. |
| `priority` | 1 = research first. `priority_reason`: finalist with open facts, could reach the top N, unlikely to reach the top N, complete, gone or rejected. |
| `finalist` | Status `shortlist` / `touring` / `applied`, a favourite tier, or rank within `quality.finalists` (10). |
| `questions[]` | Up to 8 questions from `apartmentscout/questions.py`, most decisive first; empty for gone and rejected listings. |
| `lint[]` | The listing's `apartmentscout lint` flags: `code`, `severity` (`high`, `med`, `low`), `message`, `field`. |
| `sources[]` | Per source host: listings linking to it, active ones, latest check, logged sweeps and `state` (`complete`, `partial`, `incomplete`, `no receipts`) from `research/sweeps.jsonl`. |
| `summary` | Counts over the whole search (`complete` and the `missing_*` counts are over active listings). |
| `gaps[]` (top level) | Each standard fact still missing on active listings, with a decision-impact sentence. |

Optional listing fields read by coverage: `bedroom_enclosed` (true/false once a plan, photo or visit shows
whether the bedroom is a separate room with a door and a window), `plan.printed_label` (the unit a plan
image says it is for).

## Watchlist

`watchlist.json` (dashboard export) from `watchlist:` in criteria.yaml and `watch` on listings (see
[research quality](research-quality.md#watchlist)):

```json
{"schema_version": 1, "generated": "2026-10-13", "note": null,
 "buildings": [{"key": "1-example-st", "name": "The Example Tower", "address": "1 Example St, New York, NY",
                "lat": 40.75, "lon": -73.98, "reason": "Best layouts in the area", "trigger": "a 1BR under $5,000",
                "cadence": "weekly", "url": "https://...", "last_checked": "2026-10-01", "days_since_check": 12,
                "units_seen": 3, "active_units": 1, "listing_ids": ["..."], "new_units": [], "source": ["criteria"]}]}
```

`last_checked` is the latest of the entry's own date and its units' `checked`; `new_units` are units that
appeared (new or relisted in history) on or after it. Buildings with new units come first, then the
longest unchecked. `note` explains how to add buildings when the list is empty.

`digest.json` (dashboard export; the latest `apartmentscout monitor` digest, or an empty stub):

```json
{"schema_version": 1, "generated": "2026-10-14", "note": null,
 "run": {"at": "2026-10-14T09:00:05", "date": "2026-10-14", "since": null, "dry_run": false, "offline": false,
         "targets": 6, "read": 4, "fetched": 3, "from_cache": 1, "skipped": 2, "unreadable": 0},
 "counts": {"price": 1, "gone": 1},
 "changes": [{"id": "tower-12b", "name": "The Example Tower 12B", "date": "2026-10-14", "type": "price", "field": "gross",
              "from": 4950, "to": 4800, "url": "https://example-tower.com/units/12b", "host": "example-tower.com", "note": null}],
 "unchanged": ["tower-9a"],
 "skipped": [{"id": "tower-3c", "url": "https://...", "host": "streeteasy.com", "reason": "streeteasy.com is a portal that blocks automated reads; name it in monitor.allow_hosts to try it"}],
 "unreadable": [{"id": "tower-5d", "url": "https://...", "reason": "the page says nothing usable about this unit"}],
 "blocked_hosts": {"example.com": "HTTP 403: bot check or block"}}
```

`changes[].type` and `field` are the history event types (`price` gross or net, `concession` free or lease months,
`status` available, `gone`, `relist`). `skipped` lists pages not fetched and why (a portal, a host that answered with a bot
check, no cache offline); `unreadable` lists pages that were read but gave nothing usable.

`alerts.json` (dashboard export; the change digest of `apartmentscout alerts`, see [alerts](alerts.md)): the change since the saved
baseline in `history/alerts/state.json`, else the last saved digest while it is under two weeks old, else an empty one.

```json
{"schema_version": 1, "kind": "alerts", "generated": "2026-10-15", "at": "2026-10-15T07:00:00", "search": "My search",
 "since": "2026-10-14", "first_run": false, "pending": true, "top": 10, "id": "d39fdacbee",
 "headline": "1 new, 2 price drops", "title": "ApartmentScout: 1 new, 2 price drops", "total": 3,
 "counts": {"new": 1, "drops": 2}, "tracked": 434, "fitting": 302, "quiet_new": 0, "note": null,
 "groups": {"new": [{"id": "tower-31f", "name": "The Example Tower 31F", "hood": "Chelsea", "rank": 39, "gross": 4650, "cost": 4687, "status": "new"}],
            "drops": [{"id": "orion-23a", "name": "Orion 23A", "rank": 2, "gross": 4895, "from": 5000, "to": 4895, "delta": -105, "basis": "rent"}]}}
```

`groups` keys are `new`, `fits` (adds `why`, and `from`/`to` when the price moved), `drops`, `rises` (`basis` is `rent` or `monthly cost`),
`gone` (`was_rank`, `removed`), `back`, `jumps` (`from`, `to` ranks) and `resolved` (`resolved`: the questions now answered); only
groups with changes are present. `id` follows the content, not the clock; the dashboard uses it to remember what you have seen.
